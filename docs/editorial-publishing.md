# Nodehome: редакционная публикация без платных API

Этот регламент относится **только к новым статьям**. Тексты, изображения и HTML предыдущих дней не редактируются при обычных редакционных и контрольных запусках.

## Обязательный цикл

1. По московскому времени определить дату и проверить публикации **текущих суток**. В расчёт включать только статьи с оригинальной подходящей фотографией, успешно завершившимся GitHub Actions и готовым HTML.
2. Проверить уникальность темы, `id`, `slug`, заголовка. До записи статьи изучить актуальные `content/categories.json` и `content/sections.json`.
3. Подготовить один файл `content/articles/<slug>.json` с содержательными разделами, FAQ, `publishedAt`, `categoryIds`, `topicId` и оригинальной фотографией `assets/images/<slug>-hero.webp` (или AVIF). Проверить реальный файл визуально, а не по названию.
4. Зарегистрировать `id` **ровно один раз** в `articles` соответствующей категории из `content/categories.json`. Не изменять другие категории без необходимости.
5. До коммита, если репозиторий доступен локально, выполнить `node scripts/preflight-new-articles.mjs --article content/articles/<slug>.json`. Эта проверка ловит дубли, неправильную регистрацию, неполный JSON и отсутствующий или повторно использованный файл изображения.
6. Создать коммит с JSON, реальной бинарной фотографией и регистрацией категории. При записи через GitHub API передавать бинарный файл как **blob с encoding=base64**, а не строку base64 под расширением .webp.
7. Дождаться `Build Nodehome static site`. Workflow последовательно проверяет **только новые/изменённые статьи**, собирает сайт и проверяет сгенерированные HTML/изображения. Если не прошёл шаг `Preflight new articles BEFORE site generation`, исправить указанную ошибку в сегодняшнем материале и повторить сборку.
8. Убедиться, что `site/article/<slug>/index.html` существует, ссылается на утверждённое изображение и присутствует в `site/sitemap.xml`. Только после подтверждения успешной сборки засчитывать статью.

## Изображения

Требуется **одна новая цельная фотореалистичная предметная фотография на статью**. При генерации описывать предметы, материалы, натуральный свет и конкретный ракурс. Нельзя использовать коллажи, графики, макеты отчётов, чужие фотографии, стоки, схемы, тексты, логотипы, повторно использованные обложки. Визуальная проверка обязательна: технический валидатор подтверждает формат/уникальность байтов, но **не умеет определить смысл или реалистичность изображения**.

Если после трёх итераций фото не соответствует теме, перейти к другой безопасной теме. Повторять неудачный предметный запрос до исчерпания всего слота нельзя. Публиковать плохое фото ради количества нельзя.

## Дневной объём и восстановление

Норма в Europe/Moscow: 10 после 02:00, 20 после 08:00, 30 после 14:00, 40 после 20:00. В 05:00/11:00/17:00/23:00 прежде проверять все сегодняшние новые статьи, затем компенсировать отставание новым качественным контентом. В любом запуске фактическое количество считать из реальных подтверждённых публикаций, а не из числа сделанных коммитов/черновиков. Отставание не переносится между московскими сутками.

## Что считается доказанным

- **GitHub Actions success** и готовые `site/` файлы означают, что проверенная версия собрана в репозитории.
- Визуальная проверка фотографии человеком/моделью выполняется отдельно.
- **VPS-деплой** является отдельной операцией. Сейчас README описывает ручное обновление `/opt/nodehome-source` → `/var/www/nodehome`. Сборка GitHub сама по себе не подтверждает обновление живого сайта. Для проверки либо деплоя требуется доступ к фактическому серверу.

Все технические исправления обычного редакционного цикла ограничивать новыми статьями и нужными записями категорий. Старые публикации и их фотографии не переписывать.
